## 二、核心业务流程详解
### 1. 完整执行流程
1. **请求接入**
   客户端（新/旧）发起交易请求，网关完成基础参数校验、透传客户端IP。

2. **幂等号生成**
    - 新客户端：请求携带 `requestNo`，直接复用；
    - 遗留客户端：无 `requestNo`，服务端拼接 `userId + businessType + amount + clientIp` 做 MD5 生成**请求指纹**作为临时 `requestNo`。

3. **构造 RocksDB 防重 Key**
   统一格式：
   ```
   IDEM:{businessType}:{requestNo}:{expireTimestamp}
   ```
   过期时间固定为**当前时间 + 7天**。

4. **防重校验 & 抢占锁（核心并发安全）**
    - 查询 Key 是否存在：存在 → 判定重复请求，直接拦截返回；
    - 不存在 → 立即写入 `PROCESSING`（处理中），完成“占坑”，防止并发重复执行。

5. **执行业务逻辑**
   账户扣减、订单创建、撮合交易、风控校验等核心逻辑。

6. **更新状态**
    - 业务正常：Key 对应 Value 更新为 `SUCCESS`；
    - 业务异常：Key 对应 Value 更新为 `FAILED`。

7. **异步落库**
   通过 Spring 异步线程池，将交易数据写入 MySQL，主流程不阻塞。

8. **后台自动清理**
   每日凌晨 2 点扫描 RocksDB，删除**已过期（超过7天）**的防重 Key。

### 2. 并发冲突处理
- 同一请求多线程/多重试同时到达：只有第一个请求能成功 `put(PROCESSING)`，其余请求查询命中直接拦截；
- 网络超时重试：因 `requestNo` 不变，重试请求会被正常拦截，保证幂等；
- 服务重启：RocksDB 数据持久化，重启后防重记录不丢失，规则持续生效。

## 三、关键数据规范
### 1. RocksDB Key/Value 规范
#### Key 定义
```
前缀:业务类型:请求号:过期时间戳
示例：IDEM:transfer:f8a7b9c21e3d4567:1780000000000
```
- 前缀 `IDEM`：区分防重数据，方便定时任务过滤清理；
- 业务类型 `businessType`：区分下单、转账、退款、充值等场景；
- 过期时间戳：毫秒级，用于过期淘汰。

#### Value 状态枚举
| 状态值 | 含义 |
|--------|------|
| PROCESSING | 处理中 |
| SUCCESS | 交易成功 |
| FAILED | 交易失败 |

### 2. MySQL 表（交易主表）
```sql
CREATE TABLE trade_order (
    id BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '自增主键',
    order_id VARCHAR(64) NOT NULL COMMENT '系统订单号',
    request_no VARCHAR(64) NOT NULL COMMENT '幂等请求号',
    business_type VARCHAR(32) NOT NULL COMMENT '业务类型',
    user_id VARCHAR(64) NOT NULL COMMENT '用户ID',
    amount BIGINT NOT NULL COMMENT '交易金额',
    client_ip VARCHAR(64) COMMENT '客户端IP',
    trade_status VARCHAR(16) NOT NULL COMMENT '交易状态',
    create_time BIGINT NOT NULL COMMENT '创建时间(毫秒)',
    update_time BIGINT NOT NULL COMMENT '更新时间(毫秒)',
    UNIQUE KEY uk_req_no (request_no)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT '交易主表';
```

## 四、核心组件说明
### 1. RequestIdGenerator 幂等号生成器
- 职责：兼容新旧客户端，统一产出全局唯一 `requestNo`；
- 规则：有则复用，无则基于请求关键字段生成 MD5 指纹；
- 优势：零改造遗留客户端，保证相同请求生成相同编号。

### 2. IdempotentService 防重核心服务
- 依赖：RocksDB 嵌入式存储；
- 能力：查询、加锁、状态更新；
- 特性：纯本地操作，无网络开销，微秒级响应。

### 3. RocksDB 配置类
- 场景优化：面向**高并发写入、高频点查**调优；
- 压缩：LZ4，兼顾压缩率与CPU开销；
- 内存与后台任务：适配交易万级TPS负载。

### 4. RocksDBExpireCleanTask 定时清理任务
- 执行频率：每日 02:00；
- 逻辑：遍历 `IDEM` 前缀 Key，对比时间戳，删除过期数据；
- 影响范围：后台低峰执行，不影响日间交易性能。

### 5. 异步落库
- 基于 Spring `@Async` 实现；
- 隔离实时交易与离线归档，保证主链路低延迟。

## 五、部署与运行规范
### 1. 环境依赖
- JDK：1.8+
- 中间件：无额外依赖（RocksDB 嵌入式，无需独立服务）
- 数据库：MySQL 5.7 / 8.0

### 2. 目录规划
```
/application/trade/
├── trade.jar                # 应用包
├── trade_idempotent_db/     # RocksDB 数据目录（务必单独挂载磁盘）
└── logs/                    # 应用日志目录
```
> 建议：RocksDB 数据目录挂载**SSD 盘**，进一步提升读写性能。

### 3. 启动命令参考
```bash
nohup java -jar trade.jar --spring.profiles.active=prod > logs/run.log 2>&1 &
```

### 4. 启停注意事项
1. 正常停止：先停止流量接入，再关闭应用，避免数据残留在 `PROCESSING` 状态；
2. 异常宕机：RocksDB 自带 WAL 日志，重启自动恢复数据，防重规则不失效；
3. 磁盘监控：监控 `trade_idempotent_db` 目录磁盘使用率，配合每日清理任务，阈值建议告警线 80%。

## 六、运维 & 监控指标
### 1. 核心监控项
1. **接口 QPS / TPS**：交易接口吞吐量；
2. **防重拦截次数**：统计重复请求量，异常突增需排查客户端重试/攻击；
3. **接口耗时**：重点观测 RocksDB 读写耗时（正常 < 1ms）；
4. **RocksDB 磁盘占用**：每日清理后应保持平稳；
5. **异常日志**：交易失败、RocksDB 异常、MySQL 落库失败。

### 2. 日常运维操作
1. 查看 RocksDB 数据：使用官方 `ldb` 工具查询/导出；
2. 手动清理：紧急场景可手动删除过期 Key（低峰期操作）；
3. 数据备份：通过 RocksDB `Checkpoint` 做定时快照备份。

## 七、异常场景 & 应急预案
### 场景1：RocksDB 目录损坏/无法启动
- 现象：应用启动失败，报 RocksDB 异常；
- 预案：
    1. 切换备用节点；
    2. 使用历史快照恢复 RocksDB 数据；
    3. 临时降级：短时间内关闭防重（仅应急，事后补对账）。

### 场景2：MySQL 异步落库失败
- 现象：交易成功，但 MySQL 无数据；
- 预案：
    1. 日志记录失败单据，后台补偿重试；
    2. 定时任务扫描 RocksDB 成功记录，全量补录 MySQL。

### 场景3：大量重复请求轰炸
- 现象：防重拦截指标突增；
- 预案：
    1. 网关层增加限流、IP 黑名单；
    2. 配合 RocksDB 防重双层防护。

### 场景4：遗留客户端请求指纹碰撞（极低概率）
- 现象：正常请求被误拦截；
- 预案：
    1. 临时扩容指纹字段（增加设备标识、随机因子）；
    2. 单个误拦截工单人工处理。

## 八、方案优势总结
1. **全兼容**：同时支持新客户端（自带 requestNo）、遗留客户端（无编号），存量系统零改造；
2. **高并发低延迟**：RocksDB 嵌入式本地存储，微秒级响应，支撑交易高吞吐；
3. **强幂等**：先加锁、后执行业务，彻底杜绝重复下单/扣款；
4. **数据安全**：持久化 + WAL，服务重启不丢防重记录；
5. **可运维**：自动过期清理，磁盘不会无限膨胀；
6. **架构解耦**：实时交易走 RocksDB，归档对账走 MySQL，各司其职。
