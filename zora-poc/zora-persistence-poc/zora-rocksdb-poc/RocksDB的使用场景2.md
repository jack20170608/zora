# 交易系统幂等防重组件

**用 RocksDB 做一个全局的“请求已处理标记库”，只要请求进来，先查有没有标记，没有就写入，有就直接拒绝。**
因为 RocksDB **读写微秒级、高并发、持久化不丢**，所以特别适合做交易系统的**防重/幂等**。

---

# 1. 防重 key 到底是什么？
你写的：
```
reqNo + businessType → 处理状态
```

实际落地格式是这样（字符串拼接）：
```
idempotent:${businessType}:${reqNo}
```

例子：
```
idempotent:transfer:20250405120000001
idempotent:order:20250405120000002
```

**作用：全局唯一，永远不重复。**

---

# 2. 存储的 value（处理状态）是什么？
value 一般存**状态码**，比如：
- `0` = 处理中
- `1` = 处理成功
- `-1` = 处理失败

也可以直接存 `1` 代表**已处理**。

---

# 3. 完整执行流程（交易系统标准流程）
这是**网关层必走流程**：

## 步骤 1：请求进来
```
请求 = { businessType: "order", reqNo: "20250405001", userId: "1001", amount: 100 }
```

## 步骤 2：生成防重 key
```
key = "idempotent:order:20250405001"
```

## 步骤 3：查 RocksDB 是否存在
```
value = rocksdb.get(key)
if (value != null) {
    return "重复请求，已拒绝";
}
```

## 步骤 4：不存在 → 立即写入（占坑）
```
rocksdb.put(key, "0");  // 0=处理中
```

## 步骤 5：执行业务（订单/转账/支付）
## 步骤 6：业务执行完成 → 更新状态
```
rocksdb.put(key, "1");  // 1=成功
```

---

# 4. 为什么要先写 0（处理中）？
**防止并发重复请求**：

如果两个一模一样的请求**同时到达**：
- 请求A → 查询 key 不存在
- 请求B → 查询 key 也不存在
- 两个请求同时进入业务 → **重复扣款/重复下单**

所以必须：
**查询不存在 → 立即写入 0（占坑） → 再处理业务**

这叫**抢占式防重**，生产环境必须这么做。

---

# 5. Java 真实可运行代码（生产级）
```java
// 生成防重 KEY
String key = "idempotent:" + businessType + ":" + reqNo;

// 1. 查询是否已存在
byte[] exist = rocksDB.get(key.getBytes());
if (exist != null) {
    return "重复请求，已拦截";
}

// 2. 立即占坑：标记处理中
rocksDB.put(key.getBytes(), "0".getBytes());

try {
    // 3. 执行业务：下单 / 转账 / 支付
    doBusiness(req);

    // 4. 业务成功 → 更新为成功状态
    rocksDB.put(key.getBytes(), "1".getBytes());
    return "成功";

} catch (Exception e) {
    // 5. 失败 → 更新为失败状态
    rocksDB.put(key.getBytes(), "-1".getBytes());
    return "失败：" + e.getMessage();
}
```

---

# 6. 为什么用 RocksDB 而不是 Redis？
这是**交易系统必须知道的关键点**：

1. **RocksDB 持久化，重启不丢防重记录**
   Redis 宕机可能丢数据，导致重复下单。

2. **RocksDB 写入比 Redis 更稳定**
   高并发下不会因为内存淘汰丢掉防重 key。

3. **可以设置 TTL 自动过期**
   避免无限膨胀（例如保留 24 小时）。

4. **和交易系统本地存储在一起**
   无网络开销，速度微秒级。

---

# 7. 进阶：带 TTL 自动清理（生产必加）
RocksDB 可以给**防重 key 设置过期时间**，比如 24 小时。

格式：
```
idempotent:order:20250405001:expire=1712345678901
```

后台定时任务删除过期 key 即可。

5. **执行完业务 → 更新状态**
